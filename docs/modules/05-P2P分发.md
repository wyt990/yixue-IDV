# 模块 05 — P2P 分发（客户端互助传镜像）

> 问题：1 号机已传 98%/100% 时，其它机器能否优先从「传得多的客户端」拉数据，减轻服务器压力？

---

## 1. 结论摘要

**应该支持，且对 500+ 机房价值很高。**  
一期以 **Edge HTTP 单播** 跑通；阶段 5 / 二期引入 **局域网分片互助（P2P/swarm）**，语义上正是你描述的能力。

```text
优先顺序（部署拉块时）：
  1. 同机房已持有该分片且可做种的客户端
  2. 本 Edge 缓存
  3. （一般禁止）直连 Center
```

---

## 2. 目标行为（验收级描述）

- 镜像按固定大小分片（如 4MB/8MB），每片有 hash。  
- 客户端（PE 内或 Agent 内下载器）向 **Tracker/协调器**（建议跑在 Edge）汇报：已拥有分片位图、上传带宽、负载。  
- 新加入的机器优先向 **完成度高 / 位图互补** 的对端要片；Edge 托底。  
- 1 号机 98% 时，2 号机应能从 1 号机拉到大部分片，Edge 带宽明显下降（有监控指标）。  
- 全部完成后可继续短时做种（可配），下课或任务结束后停止。

---

## 3. 架构要点

| 角色 | 职责 |
|------|------|
| Edge Coordinator | 分片清单、节点登记、peer 推荐、鉴权令牌 |
| Seeder（学生机） | 已收分片对外提供 HTTP/自定义端口上传 |
| Leecher | 多源并行下载、校验分片、汇报位图 |
| Edge Store | 权威缓存；无人做种或缺片时补给 |

### 安全

- 仅允许 **同任务 / 同镜像 ID / 短期令牌** 的 peer 互传。  
- 分片 hash 失败丢弃并拉黑异常源。  
- 默认不跨机房 P2P（避免打满核心）；跨机房只走各 Edge。

### 与「还原后客户端」关系

- **部署阶段（PE）**：P2P 最有价值（大家同时装）。  
- **系统内 Agent**：也可对增量包做种（二期）。  
- 开机还原清盘前，需停止做种并释放端口。

---

## 4. 为何不一期就做

- 依赖稳定的分片格式、任务令牌、Edge 协调器、NAT/防火墙与交换机扇出。  
- 先保证 Edge 缓存 + 限流正确，再叠加 P2P，排障更简单。  
- 一期文档与镜像格式 **预留分片清单字段**，避免二期推翻。

---

## 5. 监控指标（做了就要能看见）

- Edge 出口流量 vs 客户端互传流量占比  
- 平均任务完成时间  
- 稀有分片补给次数  
- 校验失败率  

管理端任务详情显示数据来源比例：「P2P 82% · Edge 18%」。

---

## 6. 验收清单

- [x] 同任务多机部署时，互传流量占比可统计（任务目标 `p2p_bytes`/`edge_bytes`，管理端显示比例）— **阶段 5 试点：Edge 中介 swarm**  
- [ ] 人为限制 Edge 带宽后，任务仍能靠 peer 完成（或明显快于纯受限 Edge）— 生产加固项  
- [x] 分片校验失败不会写入最终镜像  
- [x] 任务结束后做种可自动停止 — `POST /api/v1/p2p/swarm/{image_id}/stop`；pe-agent P2P 部署完成后请求停种（`stage6c-accept`）  
- [x] 跨机房默认不互连 peer（swarm 仅本 Edge）  

---

## 7. 分期

| 内容 | 分期 |
|------|------|
| 镜像分片 meta 预留 | 一期 |
| Edge 单播 + 限流 | 一期～阶段 5 |
| Coordinator + PE 内 P2P | 阶段 5 或二期 |
| Agent 增量包 P2P | 二期 |
| 组播（UDP）作为可选项 | 三期调研（校园网常限制组播） |
