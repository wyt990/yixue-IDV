# 模块 04 — 增量更新策略

> 问题：如何判断何时该使用增量更新？

---

## 1. 结论摘要

- **一期**：只做完整镜像（`content_type=full`），meta 预留 `delta` / `base_image_id`。  
- **二期**：增量是「默认推荐，可强制全量」的策略引擎，而不是每次手工猜。  
- 判定维度：**有没有合法父镜像、布局是否兼容、变更比例、网络与时间窗**。

---

## 2. 什么叫增量

在金样机或镜像库中，基于 **已存在的基础镜像 A**，生成只含差异的 **增量包 A→B**。  
终端或 Edge 需已持有 A（或能先拿到 A），再应用增量得到 B。

```text
Full(B)     ＝ 完整系统镜像 B
Delta(A→B)  ＝ 从 A 变到 B 的差量
应用： Local(A) + Delta(A→B) → Local(B)
```

---

## 3. 何时用增量（判定规则）

系统在「发布更新 / 创建同步或部署任务」时按序评估：

| 优先级 | 条件 | 结论 |
|--------|------|------|
| 1 | 目标端 **没有** 可用的 `base_image` 副本 | **必须全量** |
| 2 | 磁盘分区布局 / 分区表类型 / 磁盘规模与父镜像 **不兼容** | **必须全量** |
| 3 | `os_family` 或大版本跨越（如 Win10→Win11、跨发行版） | **必须全量** |
| 4 | 估算差量大小 ≥ 完整镜像的 **R%**（默认建议 60%～70%，可配） | **建议全量**（差量不划算） |
| 5 | 差量链过长（如超过 N 级未合并，默认 N=3） | **建议先合并出新全量** 再增量 |
| 6 | 以上皆否，且父镜像在 Edge 为 `ready` | **推荐增量** |
| 7 | 管理员勾选「强制全量」 | **全量** |

### 经验场景（给网管）

| 场景 | 建议 |
|------|------|
| 新机房首次装机 | 全量 |
| 学期初只更新几个软件/补丁 | 增量 |
| 重做分区、换系统类型 | 全量 |
| Edge 磁盘上父镜像已删 | 先同步父镜像，或改全量 |
| 多次增量后启动变慢/链路复杂 | 打一个新全量（consolidate） |

---

## 4. 谁来「判断」

1. **采集/发布时**：工具对比父镜像与金样，生成 `full` 或 `delta`，写入 meta（含估算体积、父 ID）。  
2. **任务调度时**：根据 Edge/客户端持有情况 + 上面规则表，自动选传输物件；UI 显示推荐理由，允许覆盖。  
3. **不要**让老师在无信息时纯手工猜；默认展示：「推荐增量（预计 4.2GB，父镜像已在本楼栋 Edge）」。

---

## 5. 与 P2P、缓存的关系

- 增量文件同样进 Edge 缓存，可被 P2P 分发（模块 05）。  
- 清空父镜像缓存会导致「只能全量或先拉父镜像」。  
- 校验：应用增量后必须得到与全量 B 相同的 checksum。

---

## 6. 验收清单（二期）

- [x] meta 支持 `full`/`delta` 与 `base_image_id`  
- [x] 无父镜像时自动拒绝纯增量部署并提示（deploy 拒绝 `content_type=delta`）  
- [x] 变更比例超过阈值时推荐全量（`recommend-delta` API；UI 展示可后续补）  
- [x] 管理员可强制全量（`force_full`）  
- [x] 增量应用后 checksum 与官方全量一致（`apply-delta`）  
- [x] 文档写清默认 R%、N 级链参数（本文 §3；默认 R=65%）  

---

## 7. 分期

- 一期：仅全量 + 字段预留。  
- 二期：差分生产、判定引擎、任务推荐。  
- 三期：自动合并全量、定时「打基线」。
