## 0. 结论摘要（TL;DR）

这是一个**设计文档先行、全栈自研、完成度明显高于普通课程项目**的 IDV 机房管理系统原型：Rust 5 个 crate（约 1.6 万行）+ React 19 管理端（约 5900 行）+ 自研 NTFS 稀疏采集/流式写盘 + iPXE/Alpine PE + Windows 卷过滤驱动（测试签名）。主链路「PXE → PE → 采集入库 → 边缘同步 → 流式部署」在**文件盘模拟**层面是闭环的，工程取舍（单遍流式、少内存、同机 hardlink、限速/配额、审计）有不少可圈可点之处。

但它目前是**试点/演示级产品，不是可直接交付生产的状态**，主要短板集中在四类：

1. **安全默认值**：默认 `admin/admin123` 且没有改密/登出入口；全链路明文 HTTP + CORS `Any`；Edge 列表把所有 `node_token` 返回给任何登录用户、`rotate_token` 连 readonly 都能调用；Agent/PE/P2P 多组写接口无认证；`ingest` 接口可让 Edge 指定任意本地文件路径搬移；客户端包里的内核驱动经检查**实际未签名**。
2. **文档承诺 ≠ 实现**：PostgreSQL/sqlx 0.9、HTTP Range 断点续传、短时任务令牌、Edge 断网自治、DHCP/PXE 配置由中心下发——均**未实现**；而磁盘策略 `wipe_target_partitions` 与 `write_system_only` 在代码里是同一行为。
3. **质量门禁失效**：本地按仓库钉住的 `stable`（rustc 1.99.1）复现，`cargo fmt --check` 与 `cargo clippy -D warnings` **均失败**（即仓库自带的 CI 是红的）；中心 API、Edge worker、PE Agent、NTFS 解析几乎零测试。
4. **交付物不同步/不可复现**：`web/dist` 比源码旧一个提交；PE 的 `fetch-pe-linux.ps1` 与 `build-pe-initramfs.py` 输入文件名不一致，干净仓库无法重建 initramfs；客户端包缺 `agent.toml`，`install-client.ps1` 直接失败。

综合评分（相对"校内试点可交付"标准）：

| 维度 | 评分 | 说明 |
|------|------|------|
| 架构设计 | A- | 控制面/数据面分离、组件边界清晰、文档体系完整 |
| 工程实现 | B | 核心路径有真功夫；错误处理/事务/并发细节粗糙 |
| 测试与 CI | C- | 23 个单测全部集中在 common；CI 步骤当前不通过 |
| 安全 | D+ | 认证模型有骨架，但与"可上网/机房共享网"场景不匹配 |
| 文档一致性 | B- | 总量大、结构好；关键承诺与实现脱节且未标注 |
| 可运维性 | C+ | 有验收脚本和运维手册，无服务化/容器化/指标 |
| 前端 | B- | 依赖克制、主题体系好；无角色门禁/分页/lint/test |

**建议定位**：把它作为"试点可用、生产前需一轮安全与一致性加固"的基线；先做 P0（见 §8），再谈真机试点。

- 驱动：`SysRestoreDriver`（Apache-2.0，NOTICE 声明自研，无第三方源码），当前**测试证书签名**。

### 1.3 运行时拓扑（与实现一致的部分）

```
浏览器 ──HTTP/JSON──> idv-center (axum + SQLite + images_dir)
                        │  ▲ 注册/心跳/命令/任务/上报（X-Idv-Edge-Token）
                        ▼  │
                     idv-edge (HTTP :8081 + DHCP :67/:4011 + TFTP :69 + /pxe 静态)
                        │  ▲ checkin/claim/report/blob（无认证，按 MAC）
                        ▼  │
                  学生机 PXE → iPXE → Linux PE → idv-pe-agent → 读/写磁盘
                  学生机系统内 idv-agent → 心跳/还原策略/软件/电源
```

数据面设计正确：镜像大流量走 **Edge 缓存 → 学生机**，Center 只做元数据与调度；同机部署时 Edge 用 **hardlink/copy** 绕过 HTTP 拉数 GB（`worker.rs:539-594`）。这是本项目最值得保留的架构决策。

## 2. 值得肯定的工程亮点

1. **镜像格式自研且务实**：`yixue-image-v1`（magic + header JSON + payload）+ `ntfs_used_v1` 只打包 NTFS 已用簇；采集时 **单遍流式**：pack 线程 → 有界 channel → HTTP body → Center 侧 `finalize_captured_image` 单遍哈希并**就地 patch** pending SHA（`image_format.rs:185-263`、`pe-agent/src/main.rs:677-836`）。全程 O(1) 内存，没有"先落盘再整包哈希"的二次 IO，设计得相当克制。
2. **部署流式写盘**：`deploy_reader_to_disk` 直接按 partition map 写块设备/文件，尾部校验 payload SHA（`image_format.rs:478-627`）；PE 侧用 `sync_channel + spawn_blocking` 把 HTTP 流接到写盘线程（`pe-agent/src/main.rs:1009-1120`）。
3. **采集排除优化**：`ntfs_exclude` 按 MFT/路径在**内存位图**里清 pagefile/hiberfil/Temp 簇，完全不改动金样机（`ntfs_exclude.rs:1-120`），思路正确。
4. **边缘运维细节**：缓存配额/水位告警（`worker.rs:264-309`）、同步带宽限速（`worker.rs:618-637`）、同步并发信号量、同机 hardlink 回退链、stale 任务 60s 自动收尸（`main.rs:140-153`、`tasks.rs:384-417`）。
5. **验收脚本是真联调**：`stage4-accept.ps1` 会真启动 center/edge/pe-agent、造金样盘、跑采集/入库/同步/≥5 台部署/损坏校验/CSV 导出（`deploy/scripts/stage4-accept.ps1:1-256`），不是"打印 OK"。
6. **管理端依赖克制**：3 个运行时依赖、22 个文件、4 套 Token 化主题（`themes.css`）、`request<T>` 统一封装、`ApiError` 带 status；没有为堆功能引入重型框架。
7. **过程管理意识**：`.github` CI（fmt/clippy/test/audit）、dependabot、`.editorconfig`、`.cursor` 中文提交规范、26 篇 design/plan 文档——在同类项目中少见。

## 3. 架构与关键实现走查

### 3.1 控制面（idv-center）

- 状态：`AppState { pool: SqlitePool, images_dir, software_dir, max_* }`（`state.rs`）。**类型直接绑死 `SqlitePool`**，没有数据库抽象层——这决定了"换 PostgreSQL"不是改连接串，而是改几十处类型。
- 鉴权：管理员 Bearer token（`sessions` 表，7 天，明文 token）+ Edge `X-Idv-Edge-Token`（`auth.rs:10-124`）；角色 `super/lab_admin/readonly` 通过 `require_write/require_super` 显式调用。
- 任务：capture/deploy 两类 `maintenance_tasks` + targets；Edge 领任务时把 target 置 running（`edge_agent.rs:386-473`）。
- 审计：`audit::record` 覆盖关键操作（登录、部署、模式、强推、自动登记等），支持 CSV。

### 3.2 数据面（idv-edge）

- 同步 worker：轮询 `commands/next` → `sync/purge/purge_and_sync`；下载到 `.part` 后校验 SHA、rename（`worker.rs:517-694`）。
- PE API：`checkin`（按 MAC 向 Center 领任务）、`claim/report`、`capture_upload`（落本地 capture_tmp 后 ingest 到 Center）、`image_meta/blob`（只读本地缓存）。
- DHCP/TFTP：自研最小实现，支持 full/proxy、:4011、OACK/blksize（`dhcp.rs`、`tftp.rs`）。
- P2P：Edge 内存 swarm，chunk GET/PUT + peer 注册（实验性，见 §5.4）。

### 3.3 PE 与 Agent

- PE 主链路：`iPXE checkin.ipxe` 生成脚本 → 加载 **补丁过的 initramfs**（内含下载并执行 Edge 上 pe-agent 的钩子）→ `idv-pe-agent run` → capture/deploy（`pe_api.rs:258-319`、`deploy/scripts/build-pe-initramfs.py:163-177`）。
- `idv-agent`：心跳拉 DesiredState（主机名/IP、还原策略、USB 限制、电源/软件/协助命令）+ 还原执行（卷后端/驱动状态文件）+ 开机钩子脚本。
- 还原驱动控制面：Windows 下优先真实 IOCTL/状态文件，非 Windows 或 `IDV_RESTORE_MOCK` 时走 mock（`restore_driver.rs:49-62`）。

## 5. 风险与问题清单（按严重度）

### 5.1 P0 — 生产/试点上线前必须解决

**S1. 认证与口令体系不完整（最高危）**
- 默认账号 `admin/admin123`（`db.rs:106`），登录页**预填并明文提示**默认口令（前端 `LoginPage.tsx:9-10,84-86`）。
- **没有改密接口、没有登出接口、没有管理员更新/禁用/删除**：`api/mod.rs` 只有 `auth/login`、`auth/me`、`admins` list/create；会话 7 天不可主动失效（`auth.rs:10-19`）。"务必修改默认口令"在产品内**无法完成**。
- 角色门禁有洞：`edges::create`、`modes::create/update_schedule/delete`、`tasks::create_capture` 均只取 `AuthUser` 而**不调用 `require_write()`**，`readonly` 账号可创建 Edge（拿到节点令牌）、改模式、建采集任务（`edges.rs:34-38`、`modes.rs:26-29,128-135`、`tasks.rs:109-113`）。
- 登录无速率限制/锁定；会话 token 明文入库、无清理任务；CORS `Any`（`main.rs:160-163`）。
- 全链路 **HTTP 明文**：Center/Edge/PE/Agent 都没有 TLS 配置项，文档却写 HTTPS（总纲 §9.1）。机房里用 tcpdump 即可拿到管理员 Bearer 与 Edge token。
- **Edge 令牌对任何登录用户可见**：`Edge` 模型直接序列化 `node_token`（`models.rs:604-625`），`/api/v1/edges` 列表/详情经 `EdgeView` flatten 原样返回（`edges.rs:13-32,86-94`），`readonly` 账号即可拿到全部节点令牌并冒充 Edge 调用 `/api/v1/edge/*`（注册、心跳、领任务、上报、ingest、下载任意镜像）。
- **`rotate_token` 无写权限校验**：只取 `_user: AuthUser`（`edges.rs:178-182`），`readonly` 可轮换令牌使线上 Edge 立即失联（DoS），且轮换后新令牌同样回传给调用者。
  修复：`Edge` 增加对外视图类型（token 仅创建/轮换时返回一次，列表脱敏）；`rotate_token`/`edges::create` 改 `require_super`；所有 mutating handler 统一走鉴权中间件。

**S2. 机器间接口广泛缺少认证**
- Agent 端点：`/api/v1/agent/heartbeat`、`report_restore`、`report_usb` 无任何认证（`api/agent.rs:19-22,337,361`）——任意机器可伪装 MAC 拉取策略/登记新终端/伪造还原成功。
- 软件分发与电源/协助：`software/jobs/{id}/report`、`software/jobs/{id}/blob`、`power/commands/{id}/ack`、`assist/sessions/{id}/ack` 同样无认证（仅凭 UUID 当能力）。
- PE 侧：`checkin/claim/report/capture_upload/image_blob` 全无认证；`pe_deploy_token` 默认值 `"lab-pe-token"`（`edge/src/main.rs:91-93`），且只用于 WiFi 来源的 checkin（`pe_api.rs:152-177`）。
- P2P 全部接口无认证（`p2p.rs:59-91,158-196`）。

**S3. `ingest` 的任意本地路径搬移（可被利用为文件读取/数据破坏）**
- `PUT /api/v1/edge/images/ingest?local_path=...` 会直接对 Center 主机上**任意路径**做 `relocate_file`（move 或 copy）到 `data/images/{uuid}.bin`，随后可经 `image_blob` 读回（`edge_agent.rs:575-606,353-384`）。持有任一 Edge token 的节点即可把 Center 上任意可读文件"变成镜像"。
- 若后续 `finalize_captured_image` 因 magic 不对失败，**源文件已被移走**（move 语义），留下无 DB 记录的孤儿文件并造成源文件丢失（`edge_agent.rs:625-650`）。
  修复：把 `local_path` 限制在 `images_dir`/`capture_tmp` 白名单内，先校验 magic/SHA 再移动，失败回滚。

**S4. 内核驱动实际未签名（与说明文档矛盾）**
- `deploy/client-package/` 随包说明称 `SysRestoreDriver.sys`"已用测试证书签名"（`使用说明-测试签名驱动.txt:28`），INF 还声明 `CatalogFile = SysRestoreDriver.cat`；但包内**没有 `.cat` 文件**，且用 `Get-AuthenticodeSignature` 检查包内 `.sys` 结果为 **`NotSigned`**，与 `drivers/sys-restore/.../x64/Release/SysRestoreDriver.sys` 内容一致（未签名构建产物）。
- 安装脚本在 `testsigning` 未开时只打印 WARNING 仍继续注册 BOOT_START 过滤驱动（`install-driver.ps1:21-24,50-58`），并额外执行 `bcdedit /set nointegritychecks on`（`enable-testsigning.ps1:4`）；无 Secure Boot 检查，失败可能 `0xc0000428` 无法启动。自签证书被导入 `LocalMachine\Root`/`TrustedPublisher`（`install-testcert.ps1:12-20`），而对应 PFX 私钥就在 `drivers/sys-restore/testcert/`、口令硬编码（`sign-sysrestore-testcert.ps1:55`），本机普通用户可读。
- 结论：当前客户端的"还原保护"很可能只是 `_qh_protect_state.data` 状态文件 + mock 语义（`restore_driver.rs:139-275`），驱动未真正加载；必须重新签 `.sys`/`.cat` 并在打包流水线加 `signtool verify` 拦截，生产前替换为正式（EV/WHQL）签名。
- **修复状态（2026-11-16 下午）**：已用 `YixueIDV-SysRestore-Test` 证书补签 `.sys`、生成并签名 `.cat`；安装脚本改为签名/测试模式/Secure Boot 全硬校验；新增卸载与 WinRE 恢复步骤。详见 [modules/17-驱动测试签名与蓝屏恢复.md](modules/17-驱动测试签名与蓝屏恢复.md)。

**S5. CI 实际是红的 + 交付物过期**

### 5.2 P1 — 试点前应修

**A1. 数据一致性/并发**
- 任务创建 `insert_task` + N 次 `insert_target` **无事务**（`tasks.rs:295-312`），失败会留下无 target 的孤儿任务。
- 领任务 `SELECT ... UPDATE` **非原子**（`edge_agent.rs:394-439`），两个 PE/重试同时 claim 可能重复执行同一 target（写盘任务重复执行风险高）。
- SQLite：`max_connections(5)`（`db.rs:23-26`），未显式设置 WAL、未设 `busy_timeout` 以外的并发策略。500 台 × 3s 心跳 ≈ 167 req/s，每次心跳 3~6 条 SQL，写锁竞争很容易触发 `database is locked`（sqlx 默认 busy_timeout 5s，没有 WAL，读写互斥）。
- 静态 SQL 均为参数绑定，**未发现 SQL 注入**（`format!` 只拼常量列名），这点做得对。

**A2. 规模化/网络行为**
- 同步失败无指数退避：worker 失败后按 poll 周期重试，且没有"任务级"重试计数/熔断（`worker.rs:426-465`）；部分成功（`stage`）状态只靠 UI 轮询。
- `capture_upload` 在 Edge 落一份完整临时文件再 ingest（`pe_api.rs:354-432`），采集路径需要 Edge 盘 ≥ 镜像大小；`ensure_cache_quota` 只对比整个 cache_dir 与配额（`worker.rs:482-494`），采集临时目录可能撑爆磁盘而未被配额覆盖。
- `image_blob`（Edge）无 Range、无 206、无并发限流；500 台同时部署靠交换机/缓存扛，没有连接数/带宽保护。
- P2P 仅实验：PE 的 `--p2p` 在部署时直接拒绝（`pe-agent/src/main.rs:958-963`）；`put_chunk` 把 body 全量留在内存、无大小上限（`p2p.rs:158-196`），可被局域网内任意主机用来耗尽 Edge 内存；`manifest/get_chunk` 每次把整镜像 `fs::read` 进内存（`p2p.rs:97-103,126-133`），大镜像必 OOM。
- TFTP：`serve_file` 整文件读入内存（`tftp.rs:92-97`）；块号 `u16` 无 rollover 处理（`tftp.rs:152-197`），>32MB（512B）或 >93MB（1428B）会回绕——当前只用于 iPXE 小文件所以是潜伏 bug。

**A3. 采集/部署边界**
- `capture` 上传到 Edge 的 `capture_upload` 无认证，且 `ingest` 不校验调用 Edge 是否就是任务对应 Edge（`edge_agent.rs:540-568` 只校验 target/task 关系）。
- 采集前 `exclude_temp::run_exclude_on_disk` 会尝试删除/截断金样机的临时文件（`pe-agent/src/main.rs:597-647`、`exclude_temp.rs`），虽然文档说明"运行于金样机"，但这是**对源盘的非只读操作**，建议默认关闭并显式确认。
- `finalize_captured_image` 在 Center 内执行多 GB 哈希（`edge_agent.rs:625-650` 同步等待），没有超时/进度/取消，HTTP 连接需长时间保持；PE 侧虽有心跳，前端任务超时阈值需匹配。
- Delta（`delta_images.rs:51-66,114-251`）在 HTTP 请求内同步构建/应用，GB 级要数分钟，易被反代/浏览器超时中断，且无进度字段。

**A4. 前端（结合专项评审）**
- 无角色门禁：`readonly` 仍可见所有写操作按钮；后端的 403 以英文 toast 直接暴露。
- 无 401 统一处理：token 过期后页面停在"半死"状态，不跳登录。
- 无分页/搜索/虚拟滚动，终端表 `clients.map` 全量渲染（数千终端必卡）；无 loading 三态（空态误报"没有数据"）。
- 无 lint/test/error boundary/懒加载；4 套裸 `setInterval` 轮询（Tasks 1.5s、Edges 2.5s、Dashboard 3s、PE 5s），无 visibility 暂停/去重。
- 进度文本靠正则解析后端日志（`TasksPage.tsx:352-360`），后端应返回结构化 `progress/bytes`。
- 兼容性：`themes.css:191` 使用 `color-mix()`（Chromium 111+），与文档承诺的 Chromium ≥90 冲突；无 `:focus-visible` 焦点环；暗色主题未设 `color-scheme`。
- 字体走 Google Fonts CDN（`web/index.html:7-12`），内网/信创机房离线时品牌字体失效。
- 契约靠手写 interface，已出现字段漂移（dist 缺新字段即证据）；建议 OpenAPI 生成或 zod 校验。

**A5. PE 构建链与客户端包不可开箱复现/安装**
