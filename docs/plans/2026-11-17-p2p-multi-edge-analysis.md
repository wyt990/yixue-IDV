# P2P 与多 Edge 部署分析

> 日期：2026-11-17
> 状态：Phase 1（多 Edge 按目标分流）已实现；真 P2P 未实现

## 0. 本次实现

- 新增 `maintenance_task_targets.edge_id`（迁移 024）；
- Center 创建部署任务时按机房/校区绑定、在线、镜像 `ready`、当前负载最低选择 Edge；
- 任务内轮询分配；
- Edge claim 返回目标 Edge URL，PE 从指定 Edge 下载；
- 指定 Edge 时全部目标固定该 Edge；
- 未实现故障自动重分配和客户端互传。


## 1. 当前实现状态

### 1.1 P2P

代码里有 `crates/idv-edge/src/p2p.rs`，但它是 **Edge 中介的 swarm 试点**，不是真正的客户端互传：

- 学生机把分片 PUT 到 Edge 内存；
- 其它学生机从 Edge 的 swarm 内存取分片；
- Edge 仍承担全部分片的中转和缓存；
- `manifest` / `get_chunk` 会把整个镜像读入内存，`put_chunk` 也全量留内存，大镜像会 OOM；
- P2P 接口目前没有任务令牌/鉴权；
- PE 部署明确拒绝 `--p2p`：

```text
// pe-agent: P2P still reassembles in RAM,
// refuse on real disks to avoid OOM.
```

所以：**你描述的“快机器直接给慢机器供片”目前没有实现**，只是文档/试点接口。

### 1.2 多 Edge

目前部署任务只有一个 `maintenance_tasks.edge_id`：

- 创建任务时选一个 Edge（或按机房默认 Edge）；
- 所有客户端从同一个 Edge 拉镜像；
- `claim_task` 只允许任务所属 Edge（或未指定时第一个领取的 Edge）领取；
- 多台 Edge 即使都缓存了同一镜像，也不会按客户端分流。

所以：**同一机房多 Edge 分担部署压力也没有实现**。

## 2. 必要性

### 2.1 P2P 的价值

典型场景：

```text
100 台客户端，镜像 40 GB
Edge 1 Gbps 网口
纯 Edge 单播：100 × 40 GB ≈ 4 TB 出口流量
```

理论最快也要数小时，实际受 Edge 磁盘、HTTP、交换机影响更慢。
如果快机器能给慢机器供片，Edge 出口可以下降到 20%~40%，部署时间明显缩短。

但 P2P 只把流量从 **Edge 出口** 转移到 **客户端端口/接入交换机背板**：

- 如果 100 台都在同一接入交换机，背板通常能承受；
- 如果跨交换机，上行链路可能成为新瓶颈；
- 如果客户端端口隔离/AP 隔离，P2P 直接不可用。

### 2.2 多 Edge 的价值

如果同一机房已经部署 2 台以上 Edge，且都同步了同一镜像：

- 可以按客户端分散到不同 Edge，降低单 Edge 出口压力；
- 单 Edge 故障时，另一台可接管；
- 实现难度明显低于 P2P。

但如果多台 Edge 共用同一个上行链路/交换机，出口总带宽不变，分流收益有限。

## 3. P2P 的可行性

### 3.1 真正的客户端互传需要什么

```text
Edge / Center：任务、分片清单、peer 发现、鉴权
Fast PE 客户端：保存已下载分片，运行上传服务
Slow PE 客户端：多源拉片、校验、按顺序写盘
```

难点是 **PE 端的存储**：

- PE 是内存系统，没有持久磁盘可用；
- 部署过程中目标盘正在被覆盖，不能可靠地当分片缓存盘；
- 当前 PE 部署是流式写盘，不保留完整镜像；
- 若把镜像/分片放内存，40GB 镜像直接不可行；
- 若用目标盘上的临时分区做缓存，需要预留空间，且会显著增加写盘复杂度和风险。

因此快机器即使到 90%，也只拥有内存中的部分分片，无法持续为慢机器提供早期分片；除非：

1. **镜像较小**，可以完整放内存（例如 <1~2GB，实际不现实）；
2. **预留 scratch 分区/第二块盘** 保存分片；
3. 分片只做 **有限窗口缓存**（只能帮助时间上接近的客户端，不能实现“90% 机器帮 20% 机器”）。

### 3.2 其他约束

- **客户端隔离**：交换机端口隔离/VLAN 隔离会直接阻断 peer 连接；
- **鉴权**：只允许同任务/同镜像/短期令牌，防止任意读取；
- **校验**：每片 SHA256，失败丢弃并回退 Edge；
- **做种生命周期**：快机器部署完成后如果立即重启，就不能继续做种；需要延迟重启/等待同任务完成；
- **带宽控制**：peer 上传不能打满客户端端口，否则本机写盘/系统响应受影响；
- **PE 复杂度**：需要在 PE 内运行 HTTP 服务、分片管理、重试、垃圾回收。

### 3.3 结论

P2P 在 **技术方向正确、收益明确**，但对当前 PE 架构是一次较大的改造，不能把现有 `p2p.rs` 直接当生产功能使用。

## 4. 多 Edge 的可行性

### 4.1 改造点

1. `maintenance_task_targets` 增加 `edge_id`（目标级 Edge 分配）；
2. Center 创建部署任务时，为每个目标选择 Edge：
   - 该机房/校区绑定的 Edge；
   - `image_replicas.state = ready`；
   - Edge 在线、有足够缓存空间、当前负载较低；
   - 加权最少连接/轮询；
3. Edge `claim_task` 只领取分配给自己的目标；
4. `ClaimedTask` 返回 `edge_url` / `image_url`，PE 从被分配的 Edge 下载；
5. 指定 Edge 不可用时，回退到其它已就绪 Edge 或原领取 Edge；
6. 任务详情按 Edge 汇总进度、出口流量。

### 4.2 适合先做的原因

- 不需要改 PE 的流式写盘；
- 不依赖客户端存储；
- 对 2 台以上 Edge 的机房立即见效；
- 同时提升可用性（单 Edge 故障切换）。

### 4.3 注意

- 所有候选 Edge 必须已同步同一镜像；
- Edge 的上行链路/交换机不能共用同一瓶颈；
- 需要 Edge 磁盘容量、网络指标参与调度；
- 跨 VLAN/跨机房不要默认互连。

## 5. 推荐方案

### Phase 1：多 Edge 按目标分流（优先）

```text
Center 调度器
  → 为每个目标选择 ready + 在线 Edge
  → target.edge_id
  → Edge 只领取自己的目标
  → PE 从 assigned edge_url 下载
  → 失败回退
```

收益：降低单 Edge 出口、提升可用性、风险低。
代价：需要 target 级调度、PE 返回 URL、Edge 负载指标。

### Phase 2：PE 内真正的 P2P（条件满足再做）

前置条件：

- 客户端有可用的 scratch 存储（第二块盘、预留分区，或镜像足够小）；
- 交换机允许客户端互访；
- 有任务令牌、分片校验、速率限制；
- 可接受快机器延迟重启做种。

方案：

- Edge 作为 tracker；
- 分片 4MB，SHA256；
- 快机器在 `scratch` 保存已下载分片，注册 bitmap；
- 慢机器从 peer 多源拉片，缺片回退 Edge；
- 按顺序写盘，避免随机写；
- 任务结束/全部目标完成后停种。

### Phase 3：组播/广播分发（可选）

如果交换机支持 IGMP/组播且校园网不封锁，可作为大批量同镜像分发的补充；否则优先 P2P/多 Edge。

## 6. 需要先确认的参数

1. 单镜像实际大小（10GB/40GB/100GB？）；
2. 每台客户端的端口速率、接入交换机背板/上行；
3. 机房内有多少台 Edge、是否已同步同一镜像；
4. 客户端是否允许互访（端口隔离情况）；
5. PE 是否有第二块盘/可预留 scratch 空间；
6. 部署窗口能接受多长；
7. 是否接受快机器部署完成后延迟重启做种。

## 7. 结论

- **多 Edge 分流**：必要、可行、改造量中等，建议先做；
- **真正的 P2P**：价值高，但受 PE 内存/临时存储和网络隔离限制，必须作为独立项目设计，不能直接启用当前实验性 swarm；
- 若只能选一个先做，优先 **多 Edge 按目标分流**；如果 Edge 只有一台且是 1Gbps 瓶颈，再评估 P2P + scratch 方案。
