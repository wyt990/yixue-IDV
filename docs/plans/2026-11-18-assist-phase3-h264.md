# Assist Phase 3: H.264 video path

H.264 is implemented as an optional video path on top of the phase-2 transport.

## Negotiation

1. Browser WebSocket opens and checks `VideoDecoder` availability.
2. Browser sends `{"type":"codec","codec":"h264"}` if WebCodecs exists.
3. Agent switches the capture task to H.264 and sends a `h264_config` text message
   followed by binary H.264 frames.
4. If the browser cannot configure/decode H.264, it sends `{"type":"codec","codec":"jpeg"}`
   and the Agent immediately returns to the dirty-region JPEG path.

## H.264 frame packet (version 3)

```text
magic "IDVF"
u16 version = 3
u16 flags (bit0 keyframe)
u32 sequence
u64 timestamp ms
u16 encoded width (1280)
u16 encoded height (720)
AVCC payload: repeated [u32 NAL length][NAL]
```

`h264_config`:

```json
{
  "type": "h264_config",
  "codec": "avc1.42C01F",
  "width": 1280,
  "height": 720,
  "description": "<hex avcC>"
}
```

The browser configures `VideoDecoder` with this avcC description; keyframes are
fed as `EncodedVideoChunk` and drawn to the canvas as `VideoFrame`s.

## Encoder

- OpenH264 0.9.10 (BSD-2-Clause), statically built.
- 1280x720, 2 Mbps target, 15 fps max, screen-content real-time usage.
- Keyframe interval 30 frames; SPS/PPS config is sent with every keyframe so a
  late-joining/reconnecting viewer can configure its decoder.

## Fallback

JPEG dirty-region streaming remains the default and fallback. H.264 is opt-in
through browser capability detection, so an unsupported browser keeps seeing
JPEG instead of a black screen.

## Not included

- H.265/HEVC is not enabled: browser HEVC decode is not universal and x265
  licensing is incompatible with a permissive project.
- Audio is not implemented.
