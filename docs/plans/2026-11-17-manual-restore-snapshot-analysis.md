# 手动还原快照方案分析

> 日期：2026-11-17  
> 状态：需求分析 / 方案暂缓，等待实际使用需求确认  
> 相关：模块 06（还原策略）、模块 17（还原驱动）、`restore_now` 命令

## 1. 需求

理想的手动还原流程：

```text
机房切到 manual 模式
→ 记录这一刻的系统状态（快照/还原点）
→ 管理员测试、装软件、改配置（修改可保留、可跨重启）
→ 管理员点「手动还原」并选择范围
→ 客户端重启
→ 恢复到记录点
→ 重启完成后解冻，可以继续修改
```

关键点：

- 快照必须记录“**进入手动模式时**”的状态；
- 测试期间的修改要能保留，不能每次重启都回滚；
- 手动还原是一次性操作，不能等同于“每次开机还原”；
- 还原完成后回到可修改状态。

## 2. 当前实现与差距

当前 `restore_now` 的实际动作：

```text
写 _qh_protect_state.data = 1
→ 重启
→ 卷过滤驱动丢弃“保护开启之后”的写入
→ 重启后按 manual/off 模式解冻
```

卷过滤驱动的还原点是 **“保护开启那一刻”** 的磁盘状态，不是切换 manual 时的状态。

因此：

- 切 manual 不会记录快照；
- 点击前已经写入磁盘的修改，不会因为开启保护而消失；
- 当前实现只能算“开启保护 + 重启一次”，**不是真正的 A 方案手动还原**。

> 结论：`restore_now` 可以保留作为“开启/关闭保护 + 重启”的能力，但不应作为“历史快照还原”交付。

## 3. A / B / C 方案对比

| 方案 | 行为 | 是否符合“记录这一刻” | 主要问题 |
|---|---|---|---|
| **A. 进入 manual 时创建快照，手动还原从快照恢复** | 测试修改可保留，点还原回到快照点 | **符合** | 需要快照存储 + 离线恢复环境 |
| **B. manual 一直冻结** | 修改只进重定向层，重启即回滚 | 部分符合，但每次重启都还原 | 不能跨重启保留测试修改 |
| **C. 现有镜像基线 + PE 部署** | 恢复到镜像基线 | 不符合“任意这一刻” | 和普通部署没有区别 |

B 等价于“每次重启还原”，C 等价于“重新部署”，都不满足目标。

## 4. A 方案磁盘占用

占用不是固定的“系统盘 1:1”，取决于快照实现。

### 4.1 VSS 差分快照

- 初始：几百 MB ~ 1~2 GB 元数据；
- 之后只保存快照创建后被修改的磁盘块；
- 最坏：约等于该卷**已用空间**；
- 常规：约已用空间的 20%~50%。

示例：C 盘已用 60 GB

| 改动量 | VSS 预估占用 |
|---|---|
| 小改配置/装少量软件 | 2~10 GB |
| 大量安装、Windows 更新 | 20~40 GB |
| 接近全盘改动 | 最多约 60 GB |

VSS 需要设置最大空间并监控；空间不足时旧快照会被自动删除，还原点失效。

### 4.2 全量 WIM/镜像快照

- 未压缩：约 **1:1 已用空间**；
- WIM 压缩后：约 **0.6~0.9 倍已用空间**；
- 已压缩/加密数据可能接近 1:1。

### 4.3 全量块复制

约 **1:1 已用空间**，恢复最直接，但占用最大、耗时最长。

### 4.4 保护范围放大

| 范围 | 占用 |
|---|---|
| 仅 C 系统盘 | 按 C 已用空间计算 |
| `all_fixed`（C/D/E） | 按所有受保护卷已用空间之和计算 |

示例：

```text
C 已用 60 GB + D 已用 200 GB
VSS 最坏 ≈ 260 GB
```

单台测试机可以接受；500 台每台几十 GB 时，需要集中存储/去重/只做系统盘，否则不现实。

## 5. A 方案实现路线

### A1. VSS 差分 + Windows PE 恢复（推荐方向）

流程：

1. 切 manual / 点击“创建还原点”时，对受保护卷创建 VSS shadow；
2. 记录 shadow ID、卷、时间、范围到 Center/Agent 本地；
3. 手动还原时重启进入 Windows PE；
4. PE 中挂载 VSS 快照，写回系统卷；
5. 重启进 Windows，解冻。

优点：

- 空间占用最小；
- VSS 创建快，支持打开文件一致性。

难点：

- 当前 PE 是 Alpine Linux，不能直接读 Windows VSS；
- 需要新增 Windows PE 恢复环境、VSS 挂载/写回脚本；
- 系统盘恢复必须在离线环境完成。

### A2. 全量 WIM/镜像 + 现有 PE

流程：

1. 在 manual 创建点通过 VSS/离线捕获生成 WIM；
2. 手动还原时用现有 PXE/PE 部署 WIM 写回。

优点：

- 复用现有镜像/部署体系；
- 恢复流程成熟。

缺点：

- 占用接近 1:1 已用空间；
- 捕获/恢复耗时较长；
- 快照点不是“瞬时”而是“捕获完成时”。

### A3. 驱动级持久快照（远期）

扩展卷过滤驱动，维护持久化重定向层/快照，手动还原时丢弃 overlay。

- 空间可能最小；
- 但需要内核驱动改动、跨重启映射持久化，风险和周期最大；
- 暂不作为近期方案。

## 6. 推荐结论（暂定）

- **A 是正确产品方向**；
- 近期若只做少量测试机、主要保护 C 盘：优先评估 **A1（VSS + Windows PE）**；
- 若想尽量少改架构：评估 **A2（WIM + 现有 PE）**；
- 在需求未明确前，不建议直接上 A3 驱动改造。

## 7. 待确认参数

后续实施前需要确认：

1. 快照范围：仅 C，还是 C/D/E 全部？
2. 规模：几台测试机，还是 500 台机房？
3. 快照存放位置：本机数据盘、Edge 缓存，还是 Center 集中存储？
4. 可接受的还原时间：秒级、分钟级，还是进 PE 几分钟？
5. 是否接受“创建还原点需要重启/进入 PE”，还是必须 Windows 在线创建？

## 8. 当前代码状态

- `restore_now` 命令和 UI 已存在；
- 行为是“开启保护 + 重启一次”，**不是快照还原**；
- 在 A 方案落地前，不应把它宣传为“回到手动模式开启时”；
- 后续可以保留该命令作为低层能力，或替换为真正的快照还原流程。
